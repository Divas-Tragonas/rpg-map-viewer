API SPEC — RPG Map Viewer
========================

BASE URL: configurat via NEXT_PUBLIC_API_URL (sense barra final)
WS BASE : substituir http per ws → ws://[host]:3000


## TIPUS Enemy

{
  id: string          // generat per la API
  name: string        // ex: "Goblin"
  color: string       // hex, ex: "#3a8a3a"
  hpMax: number       // enter >= 1
  R: number           // radi token en px, enter 8–200
  sm: number          // multiplicador escala, decimal 0.1–5.0
  imageData?: string  // opcional, base64 "data:image/png;base64,..."
  project: string     // text lliure (trim, màx. 60); '' = sense projecte
  category: string    // text lliure (trim, màx. 60); '' = sense categoria
  xp: number          // enter >= 0: XP que dona en ser derrotat (0 als documents antics)
  reachFt: number     // v5: abast cos a cos en peus, enter 0–300 (5 per defecte i als documents antics)
  resistances: DamageType[]          // v5: meitat de dany ([] per defecte)
  vulnerabilities: DamageType[]      // v5: doble de dany
  immunities: DamageType[]           // v5: cap dany
  nonMagicResistances: DamageType[]  // v5: meitat de dany només si l'atac NO és màgic
}

DamageType = 'acid' | 'bludgeoning' | 'cold' | 'fire' | 'force' | 'lightning' | 'necrotic'
           | 'piercing' | 'poison' | 'psychic' | 'radiant' | 'slashing' | 'thunder'

`project` i `category` serveixen per agrupar els enemics al back office i a la
Biblioteca del DM (`src/lib/enemy-groups.ts`). No hi ha cap col·lecció de grups:
el frontend treu els valors de la mateixa llista. GET els retorna sempre (també
als documents antics, amb ''). POST els accepta opcionals ('' per defecte); PUT
només els toca si venen al body (`category: ''` la buida). Més de 60 caràcters →
400. Una API anterior no els retorna: el back office ho detecta
(`apiSupportsGroups`) i ho avisa en lloc de perdre'ls en silenci.


`xp` (v4.67): GET el retorna sempre; POST l'accepta opcional (0); PUT només el toca si ve
al body. El visor el copia al token en afegir l'enemic i el reparteix en acabar el combat.


Defenses (v5): GET les retorna sempre (amb els valors per defecte als documents antics);
POST les accepta opcionals; PUT només toca les que vénen al body. Un tipus fora de la llista
→ 400. El visor les copia al token en afegir l'enemic (`LibEnemy.defenses`) i no les envia mai
a les pantalles de jugador. Una API anterior no les retorna: el visor fa servir 5 ft i cap
resistència.


Bloc de 5e (v5 snapshot 7, desplegat): camps opcionals de l'Enemy
  cr: string ('' o '0','1/8','1/4','1/2','1'…'30'; '' per defecte)
  ac?: int 0–40, speedFt?: int 0–200, move?: string (màx. 80)
  abilities?: { str, dex, con, int, wis, cha: int 1–30 }   (sencer o absent)
  saves?: { str?, dex?, con?, int?, wis?, cha?: int −5–20 }  (bonificació total)
  nonMagicImmunities: DamageType[]  ([] per defecte)
  conditionImmunities: ConditionId[] ([] per defecte; blinded, charmed, deafened, exhaustion,
                       frightened, grappled, incapacitated, invisible, paralyzed, petrified,
                       poisoned, prone, restrained, stunned, unconscious)
  attacks: [{ name (1–80), kind: 'melee'|'ranged'|'thrown', reachFt?, rangeFt?, longFt?,
              bonus? (màx. 10), damage? (màx. 40), damageType? }]  ([] per defecte)
  traits: string[] (cada un màx. 300; [] per defecte)
GET els retorna sempre (defaults als documents antics); POST opcionals; PUT només toca els que
vénen. El back office els edita (`StatBlockEditor`, amb «Omplir des del bestiari») i el visor els
copia al token (`LibEnemy.block`) i els refresca de la llista de la BD (`lib/db-enemies.ts`).


## TIPUS Character (fitxa de personatge, v4.67)

{
  id: string
  name: string               // trim, 1–80
  player: string             // màx. 60 ('' per defecte)
  race: string               // màx. 60
  className: string          // màx. 60 (p. ex. "Mag 1")
  level: number              // enter 1–20 (la API NO el calcula: el DM confirma les pujades)
  xp: number                 // enter >= 0. Només el mouen els endpoints d'XP
  hpMax: number              // enter >= 1
  ac: number                 // enter >= 0
  speed: number              // enter >= 0 (peus)
  passivePerception: number  // enter >= 0
  portrait: string           // dataURL o '' (màx. 1 MB)
  notionUrl: string          // màx. 500
  sheet: object              // OPAC (màx. 512 KB): la resta de la fitxa. Format al frontend:
                             // `CharacterSheet` a src/lib/characters.ts (background, alignment,
                             // initiative, profBonus, hitDie, abilities, saves, sections[])
  createdAt: string; updatedAt: string
  xpLog?: [{ amount, reason, source, awardId, at }]   // només a GET /characters/:id; 200 últims
}

POST/PUT rebutgen `xp` i `xpLog` amb 400 (només es mouen per POST .../xp).


## TIPUS Session (Partida)

Estat complet d'una partida desat al servidor (back office). Substitueix la
necessitat del save/load a .json local, però el .json es manté per a ús offline.

Session (resposta completa, GET /sessions/:id):
{
  id: string          // generat per la API
  name: string        // ex: "Sessió 3 — La cripta"
  data: object         // JSON OPAC amb l'estat complet (veure sota). La API NO
                       // n'ha de validar l'estructura interna: el tracta com a blob.
  createdAt: string    // ISO 8601
  updatedAt: string    // ISO 8601
  sizeBytes: number    // mida de `data` serialitzat (bytes) — informatiu
}

SessionMeta (element de la llista, GET /sessions — SENSE el camp pesat `data`):
{
  id: string
  name: string
  createdAt: string
  updatedAt: string
  sizeBytes: number
}

Sobre `data`: és exactament l'objecte que el frontend ja serialitza avui al
save .json (camps: version, vis, pos, zoom, panOffset, players, conditions,
defeated, paintedZones, strokeHistory, grid*, tokenSizeOverride, libEnemies,
walls, rooms, turn, drawCanvas, i els pesats bgData/bgMimeType, mapSize;
les partides velles poden portar també psdStruct, psdInfo, layerImageUrls). Pot contenir imatges base64 i, al fons, fins i tot un
vídeo → el payload pot arribar a desenes de MB. La API l'ha de tractar com a
blob opac (sense validar-ne els camps) perquè el frontend pugui evolucionar
l'estat sense tocar la API.


## ENDPOINTS HTTP

GET    /enemies          -> Enemy[]  (200)
POST   /enemies          -> Enemy    (201)  body: Enemy sense id
PUT    /enemies/:id      -> Enemy    (200)  body: camps parcials sense id
DELETE /enemies/:id      -> 204

GET    /sessions         -> SessionMeta[]  (200)   // llista lleugera, SENSE `data`
GET    /sessions/:id     -> Session        (200)   // partida completa, AMB `data`
POST   /sessions         -> Session        (201)   body: { name, data }
PUT    /sessions/:id     -> Session        (200)   body: { name?, data? } (sobreescriu)
DELETE /sessions/:id     -> 204

GET    /characters           -> Character[] SENSE xpLog (200)        JWT admin
GET    /characters/:id       -> Character AMB xpLog (200)            JWT admin
POST   /characters           -> Character (201)                      JWT admin
PUT    /characters/:id       -> Character (200)                      JWT admin  (parcial)
DELETE /characters/:id       -> 204                                  JWT admin
POST   /characters/:id/xp    -> Character (200)                      JWT admin
       body { amount: int ≠ 0 (±100000), reason?: ≤120, source?: ≤60, awardId?: ≤64 }
POST   /characters/xp        -> Character[] (200)                    JWT admin
       body { awards: [{ id, amount }] (1–20, ids únics), reason?, source?, awardId? }

Notes /characters:
- Totes les rutes demanen el JWT del back office, també les de llegir: el DM ha d'estar
  connectat al back office (com per a /sessions). Sense, el visor amaga les fitxes.
- XP atòmica ($inc) i mai per sota de 0. `awardId` = idempotència: si ja és a l'xpLog, no
  es torna a sumar (el visor envia `combat-<temps>` al repartiment del combat, `dm-<temps>`
  i `bo-<temps>` a les entregues a mà). Al lot, un id que no existeix → 404 i no s'aplica cap.
- `source` que fa servir el visor: 'combat', 'dm', 'backoffice'.
- La fitxa que es mostra a les pantalles de jugador NO passa per la API: viatja dins del
  STATE (camp `sheet`, veure sota).

Notes /sessions:
- Auth: PROTEGIT amb el JWT admin (Authorization: Bearer <token>), igual que les
  rutes del back office. El frontend adjunta el token des de la cookie `admin_token`
  (ja el llegeix `src/lib/api.ts`). Sense token vàlid → 401. El DM ha d'estar
  loguejat al back office perquè el desar/carregar al servidor funcioni; si no ho
  està, el frontend ho detecta i recorre al save/load a .json (offline).
- Límit de body: el body JSON pot ser gran (imatges/vídeo en base64) → cal
  apujar el límit del parser (p. ex. express.json({ limit: '80mb' })). Emmagatzematge
  tolerant a documents grans (GridFS o fitxer + metadades a Mongo si se supera el
  límit BSON de 16MB amb fons de vídeo).
- 413 (payload massa gran) si se supera el límit; el frontend ho gestiona.


## AUTH — POST /auth/login (existent, no documentat fins a la v4.81)

POST   /auth/login       body { password: string }
       200 → { token: string }   // JWT HS256 signat amb JWT_SECRET (el mateix que fa servir
                                 // el `middleware.ts` del frontend per protegir /admin/*)
       401 → { error: string }
El frontend desa el token a la cookie `admin_token` (escrita per JS, 7 dies) i l'envia com a
`Authorization: Bearer` a /sessions i /characters. Proposta de canvi: veure «lot Dades» al final.

## WEBSOCKET SYNC — GET /sync?role=dm|client[&key=...]

Connexió WebSocket per sincronitzar DM i clients (iPad, etc.), tant en xarxa
local com per internet (via Tailscale Funnel).

### Connexió

  ws://[host]:3000/sync?role=dm       → client DM (laptop)
  ws://[host]:3000/sync?role=client   → client jugador (iPad)

### Autenticació (SYNC_KEY)

Si el servidor té `SYNC_KEY` configurat (obligatori quan s'exposa públicament
via Tailscale Funnel), **tots** els clients han d'incloure `&key=<SYNC_KEY>`
a la URL de connexió, o el servidor tanca la connexió amb codi `4401` i motiu
`"invalid key"`. Si `SYNC_KEY` no està definit al servidor, el paràmetre és
ignorat (accés obert, ús només LAN).

Al frontend, la clau es llegeix de `NEXT_PUBLIC_SYNC_KEY` (`src/lib/ws.ts`) i
ha de coincidir amb el `SYNC_KEY` configurat al `.env` del servidor de la API.

### Protocol de missatges

Tots els missatges JSON tenen camp `type` (string).
Els missatges binaris (ArrayBuffer) es reenvien directament sense parsing.

#### DM → Servidor → Clients (rol=client rep aquests tipus)

| type                | Contingut addicional                                            | Descripció                         |
|---------------------|-----------------------------------------------------------------|------------------------------------|
| STATE               | Camps de BCStateMessage (vis, pos, cam, zoom, players, gridSnap, activeSpells, measure...) | Delta d'estat       |
| STRUCT              | Estat complet inicial (BCStructMessage, inclou cam + activeSpells + measure) | Enviat en reconnexió / late join |
| BG_META             | { mimeType: string, withFade?: boolean }                        | Capçalera del frame binari BG      |
| EXPOSITOR_SHOW_META | { mimeType: string }                                            | Capçalera del frame binari expositor |
| STROKE              | { points, color, size, tool }                                   | Traç de dibuix                     |
| CLEAR_DRAW          | —                                                               | Netejar canvas                     |
| UNDO_DRAW           | { strokeHistory: StrokeData[] }                                 | Desfer traç                        |
| POINTER             | { pos: Point | null }                                           | Cursor DM                          |
| MEASURE             | { a: Point | null, b: Point | null }                            | Regla de mesura                    |
| SPELL               | { spell: Spell }                                                | Animació de spell                  |
| DELETE_SPELL        | { id: string }                                                  | Eliminar spell d'àrea actiu        |
| BOSS_INTRO          | { tokenId, bossName, tokenPos, cam?, portraitDataUrl, style?, sprite?, party?, extras?, message? } | Cinematica boss (cam: CamRect mapa; style: pixel art; extras: enemics del grup) |
| BOSS_INTRO_SKIP     | —                                                               | Saltar cinematica                  |
| EXPOSITOR_HIDE      | —                                                               | Amagar expositor                   |
| EXPOSITOR_SYNC      | { zoom, panXNorm, panYNorm, kbTxPct, kbTyPct }                  | Sincronització expositor           |
| TEXTREVEAL_SHOW     | { text: string, pos: number, cps: number, fadeMs: number }      | Mostrar revelador de text          |
| TEXTREVEAL_SYNC     | { pos: number, cps: number, fadeMs: number }                    | Front de revelació (~30fps)        |
| TEXTREVEAL_HIDE     | —                                                               | Amagar revelador de text           |
| TOKEN_RELAY         | { id: number | string, x: number, y: number }                   | Relay d'un TOKEN_MOVE d'un client a la resta de clients (veure sota) |
| (binary frame)      | ArrayBuffer (imatge o vídeo)                                    | Segueix BG_META o EXPOSITOR_SHOW_META |

#### Client → Servidor → DM (rol=dm rep aquests tipus)

| type         | Contingut addicional                           | Descripció                          |
|--------------|------------------------------------------------|-------------------------------------|
| TOKEN_MOVE   | { id: number | string, x: number, y: number }  | Client mou token (iPad drag)        |
| PLAYER_READY | —                                              | Client connectat, sol·licita STRUCT |
| VIEWPORT     | { id: string, w: number, h: number }           | Mida del canvas d'aquella pantalla  |

`VIEWPORT` l'envia cada client en connectar, en redimensionar la finestra i cada
15s (heartbeat). El servidor el reenvia al rol=dm com qualsevol altre missatge
client→dm. El DM en fa la llista de pantalles connectades del seu HUD i hi
calcula quant de mapa veu de més cadascuna. Entre finestres del MATEIX ordinador
viatja pel BroadcastChannel, així que el xip funciona igualment sense la API.

El camp `cam` de STATE/STRUCT no va requerir cap canvi al servidor: és un camp
més dins d'un missatge que ja es reenvia opac. Igual el camp `spellPreview`
(SpellPreview | null: la màgia que el DM està apuntant, perquè els jugadors en
vegin el radi): viatja dins del STATE, throttled a ~20 Hz mentre s'apunta.

Tampoc no han calgut canvis per a l'app Píxel (v4.38): els camps `appStyle`
('classic' | 'pixel') i `tileLive` (parts animades del mapa de caselles) viatgen
dins del STATE.

Tampoc no ha calgut cap canvi per als diàlegs de personatges (v4.42): el camp
`dialog` (DialogSync | null, veure `src/types/index.ts`) viatja dins del STATE i del
STRUCT, que el servidor ja reenvia opacs. Porta: id, line, kind ('scene' | 'bubble'),
tokenId, name, voice, text, style, cps, age (ms que feia que la línia havia començat
quan s'ha enviat), done, bars, cam (CamRect | null) i options. Pocs centenars de bytes;
el retrat no hi va (cada pantalla el treu del token). `null` = no hi ha cap diàleg.

Tampoc no ha calgut cap canvi del WebSocket per a les fitxes (v4.67): el camp `sheet`
(SheetShow | null: foto de la fitxa amb les parts que tria el DM) viatja dins del STATE i del
STRUCT, només quan canvia.

Tampoc no ha calgut cap canvi per a l'Escena (imatge + subtítols, v5 snapshot 16): els camps
`scene` (SceneShow | null: id, text, media { id, mimeType } | null, opts) i `sceneSync`
(SceneSync: id, pos, cps, fadeMs, view { zoom, panXNorm, panYNorm, kbTxPct, kbTyPct }, ~30 fps)
viatgen dins del STATE. Des de la v5 snapshot 17, `scene.slides` (SceneMediaRef[]) porta totes
les diapositives (imatges) de l'escena i `media` la d'ara. El mèdia reaprofita EXPOSITOR_SHOW_META amb dos camps més
(`target: 'scene'`, `id`) + el frame binari; el servidor els reenvia opacs.

⚠️ Nota (2026-11-08): `ROUTABLE_TO_CLIENTS` (app/src/modules/sync/sync.routes.ts) NO inclou
TEXTREVEAL_SHOW / TEXTREVEAL_SYNC / TEXTREVEAL_HIDE, tot i que surten a la taula de dalt: el
Revelador de text no arriba als clients per WS (només per BroadcastChannel). Si es vol a la
tablet, cal afegir-los a la llista de la API.

Tampoc no ha calgut cap canvi per al mode Fòsfor (v4.92): el camp `phosphor` (boolean, lleuger)
viatja dins del STATE i del STRUCT, que el servidor ja reenvia opacs.

Tampoc no ha calgut cap canvi per als llocs de les missions (v4.59): el camp `curtain`
(SceneCurtain | null: { closed, scene, title }) viatja dins del STATE i del STRUCT. És el fos a
negre del canvi d'escena; el mapa nou arriba pel BG de sempre.

Des de la v4.40 els sprites són a l'app (`public/sprites/`) i cada pantalla els
carrega del mateix lloc: el camp `spritePack` del STATE i el `packId` del
PLAYER_READY (v4.38–v4.39) ja no s'envien.

Per verificar el contracte del relay: `node scripts/check-sync.mjs [ws://host:3000] [SYNC_KEY]`

### Relay de moviment de tokens entre clients (TOKEN_RELAY)

Quan un client (p. ex. un iPad) mou un token de jugador, envia `TOKEN_MOVE`
al DM. El DM el processa i, per propagar el moviment a la RESTA de pantalles de
jugador (altres iPads/teles), reenvia un `TOKEN_RELAY { id, x, y }` (rol=dm).

El servidor ha de reenviar `TOKEN_RELAY` als clients EXACTAMENT igual que
qualsevol altre missatge dm→client (STATE, POINTER, etc.). Si el servidor
filtra per tipus i descarta els tipus desconeguts, cal afegir `TOKEN_RELAY`
a la llista de tipus reenviats dm→client; altrament els altres clients mai
reben el moviment i les seves pantalles no es refresquen (només es veu al
mateix ordinador via BroadcastChannel, no cross-device via WebSocket).

`TOKEN_RELAY` NO s'ha de cachejar com a estat (no és STRUCT); només reenviar.

### Late join

Quan un client (role=client) es connecta, el servidor li envia immediatament
l'últim missatge STRUCT rebut del DM (si n'hi ha). Això sincronitza l'estat
sense que el DM hagi de fer res.

### Reconnnexió

El client (`src/lib/ws.ts`) es reconnecta automàticament als 2 segons si la
connexió es tanca. En reconnectar, envia `PLAYER_READY` per demanar STRUCT.

### Exemple de flux iPad

  iPad connecta ws://[laptop-LAN-IP]:3000/sync?role=client
  → Servidor envia STRUCT cached (si hi ha)
  → iPad envia PLAYER_READY
  → DM rep PLAYER_READY → envia BG_META + binary + STRUCT
    (+ TEXTREVEAL_SHOW si el revelador de text està actiu, perquè el client
     que reconnecta recuperi el text: els TEXTREVEAL_SYNC sols no porten text)
  → iPad rep tot i mostra el mapa
  → Usuari arrossega token → iPad envia TOKEN_MOVE
  → DM rep TOKEN_MOVE → actualitza posició localment
  → DM reenvia TOKEN_RELAY { id, x, y } (rol=dm)
  → Servidor reenvia TOKEN_RELAY a la resta de clients (altres iPads/teles)
  → Els altres clients fusionen la nova posició del token i refresquen

### Variables d'entorn (opcional per a LAN des de v3.71)

  NEXT_PUBLIC_API_URL=http://[laptop-LAN-IP]:3000

Des de v3.71 el frontend dedueix la URL del WS en runtime: si NEXT_PUBLIC_API_URL
no està definida (o apunta a localhost i la pàgina s'ha carregat des d'un altre
host), es connecta al host de window.location amb port 3000. Per tant, per a l'ús
en LAN (tablet → http://[laptop-LAN-IP]:3001/player) no cal configurar res: la API
només ha d'escoltar a 0.0.0.0:3000.
